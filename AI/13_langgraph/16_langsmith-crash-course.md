## 🎯 Overview
A ~2.5-hour crash course on **LangSmith**, a unified **observability and evaluation** platform for LLM applications. The video motivates the need for observability through three real-world debugging nightmares (latency, cost, hallucination), formally defines observability and LangSmith, then walks through **hands-on tracing** of a simple LLM app, a sequential chain, a RAG app, a ReAct agent, and finally a LangGraph workflow. It closes with an overview of the broader **LLMOps** features LangSmith offers beyond observability. Prerequisites: familiarity with LangChain and the LangGraph taught so far in the series.

## 🧠 Key Concepts

### Why observability? Three motivating scenarios

**Scenario 1 — LLM workflow (cover-letter generator).** A startup builds a tool where a student uploads a JD (link or PDF); the tool studies the JD, fetches the student's portfolio/resume/projects from Google Drive, matches skills, generates a tailored cover letter, and proofreads it for tone/conversion. Normal end-to-end **latency is ~2 minutes**. One day users complain the site is slow — the same task now takes **7–10 minutes**, users get frustrated and leave (revenue loss). The workflow is a **complex multi-stage LLM pipeline** (study JD, fetch docs, match, generate, proofread — each an LLM interaction). You only see the initial input, final output, and total time — **not the per-stage breakdown**, so you can't tell which stage ate the extra 8 minutes (maybe a bad code push made it scan the *entire* Drive instead of one folder). **Problem: increased latency, culprit unknown.**

**Scenario 2 — Agent (research assistant).** An autonomous agent takes a topic (e.g., "solar energy"), fetches academic papers (Google Scholar / arXiv), extracts key points, summarizes into a report, and lets the user chat about it. Cost is ~50 paise/report. Suddenly some reports cost **₹2** while others stay at 50 paise — a **cost spike** that's disastrous at scale. Cause: a minor prompt change ("keep generating until the report is truly the best") made the agent **loop** — re-fetching, re-reading, re-summarizing for certain topics. Agents are **autonomous** (goal → reason → act → check → repeat), the error is **intermittent**, leaves **no error trace**, and spans **multiple stages** — extremely hard to debug. **Problem: cost/token spike, culprit unknown.**

**Scenario 3 — RAG (HR-policy chatbot).** A RAG chatbot answers new-joiner questions (leave policy, notice period, insurance) from a company knowledge base. It starts **hallucinating** — inventing answers and spreading misinformation (e.g., telling an employee there's no limit on leaves). RAG hallucination usually comes from one of two failure points: **(1) retriever errors** — wrong/irrelevant chunks fetched (e.g., someone set the number of retrieved docs `n = 1`, too few), or **(2) generator errors** — the LLM hallucinates (weak local model, a provider upgrade, or a **lenient prompt** that doesn't strongly force answering only from context). You can't see inside, so you can't tell whether the **retriever** or the **generator** is at fault. **Problem: hallucination, culprit unknown.**

### What is observability
> *Observability is the ability to understand a system's internal state by examining its external outputs — like logs, metrics, and traces. It lets you diagnose issues, understand performance, and improve reliability by analyzing data generated by the system. Essentially it's about being able to answer why something is happening within a system, even if you didn't anticipate the problem.*

The common thread across all three scenarios: LLM systems are **non-deterministic** — the *same input can yield different outputs* (unlike a calculator, always returning the same result). This makes bugs (latency/cost/hallucination) hard to debug: they leave **no proper error trace**, and the systems are **complex black boxes** with no explainability. Observability turns the black box into a **white box** — you run the app end-to-end, **trace** the execution, store it, and later inspect **component by component** what happened.

### What is LangSmith
> *LangSmith is a unified observability and evaluation platform where teams can debug, test, and monitor AI app performance.*

It lets you bring observability to any LLM app: run the app, and LangSmith **traces the whole execution at a granular level** — recording every component's inputs, outputs, and time taken.

### What LangSmith traces
- **Inputs and outputs** of every execution.
- **Every intermediate step** (e.g., in RAG: question → retriever → context → prompt → LLM → parser).
- **Latency** — at both application and component level.
- **Token usage** and **cost** (input and output tokens), based on the model used.
- **Errors** in any component.
- **Tags** — system-generated (e.g., auto-detecting the model name like GPT-4o) and custom.
- **Metadata** — system (LangChain version, dependencies) and custom.
- **User feedback**, optionally attached to a trace.

### Three core concepts: Project, Trace, Run
Using a simple app (user question → prompt → LLM → parser → answer):
- **Project** = the *entire* LLM application.
- **Trace** = a *single end-to-end execution* of the project. Ask "What is the capital of India?" → the whole system runs once → that's one trace. The app runs many times → many traces.
- **Run** = the execution of *each component* within a trace. A `prompt | model | parser` chain produces **three runs** per trace (one per component), each with its own input, output, latency, and metadata.

Hierarchy in the UI: **Tracing Projects → Project → Traces → Runs.**

## 🔧 Code / Implementation

### Environment setup (`.env`)
Tracing is enabled purely through environment variables — **no code change to the app is needed** to start tracing.
```bash
# .env
OPENAI_API_KEY=sk-...              # models are OpenAI
LANGCHAIN_TRACING_V2=true          # must be true to trace
LANGCHAIN_ENDPOINT=https://api.smith.langchain.com
LANGCHAIN_API_KEY=ls-...           # from LangSmith Settings -> Personal Access Token
LANGCHAIN_PROJECT=LangSmith Demo   # a project by this name is auto-created in LangSmith
```
Whatever name you set in `LANGCHAIN_PROJECT` becomes the project on LangSmith, and all tracing for that run goes there.

### Setup steps
1. `git clone` the course GitHub repo, open in VS Code.
2. Create + activate a virtual env: `python -m venv myenv` → activate.
3. `pip install -r requirements.txt`.
4. Create a LangSmith account → **Settings** → create an **API key** (type: Personal Access Token).
5. Create the `.env` file above.

### 1) Simple LLM call
A basic `prompt | model | parser` chain (`ChatOpenAI` + `StrOutputParser`, prompt via `PromptTemplate.from_template`). Just run it — LangSmith traces automatically. Ask "What is the capital of Peru?" → "Lima". In the UI, open **Tracing Projects → LangSmith Demo → the trace**; you'll see input, output, error status, latency, token usage, and cost, and drilling into the trace shows the three runs (`PromptTemplate`, `ChatOpenAI`, `StrOutputParser`) each with per-run input/output/latency.

### 2) Sequential chain (project name, tags, metadata, run name from code)
A two-step app: generate a detailed report on a topic, then a 5-point summary of that report.
```python
import os
os.environ["LANGCHAIN_PROJECT"] = "Sequential LLM App"   # overrides the .env project name

model1 = ChatOpenAI(model="gpt-4o-mini", temperature=0.7)   # report generation
model2 = ChatOpenAI(model="gpt-4o", temperature=0.5)        # summarization

# ... build: prompt1 | model1 | parser | prompt2 | model2 | parser

config = {
    "tags": ["llm_app", "report_generation", "summarization"],
    "metadata": {
        "model1": "gpt-4o-mini",
        "model1_temp": 0.7,
        "parser": "StrOutputParser",
    },
    "run_name": "sequential_chain",   # overrides the auto-generated "RunnableSequence" name
}

result = chain.invoke({"topic": "Unemployment in India"}, config=config)
```
Setting `LANGCHAIN_PROJECT` in code **overrides** the `.env` value. Tags/metadata/`run_name` are passed through the `config` dict on `invoke`. In the UI, tags and metadata show at trace level (and each run also carries its own auto tags like "sequence step 1/2/…" and model-specific metadata).

### 3) RAG application
A simple RAG over the *Introduction to Statistical Learning* PDF:
```python
os.environ["LANGCHAIN_PROJECT"] = "RAG Chatbot"

# 1. load
loader = PyPDFLoader(pdf_path)          # 441 pages -> 441 Document objects
docs = loader.load()

# 2. chunk
splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=150)
chunks = splitter.split_documents(docs)

# 3. embed + retriever
vector_store = ...        # embeddings -> vector store
retriever = vector_store.as_retriever()

prompt = ChatPromptTemplate.from_messages([
    ("system", "Answer only from the provided context. If not found, say you don't know."),
    ("human", "Question: {question}\nContext: {context}"),
])

def format_docs(docs):
    return "\n\n".join(d.page_content for d in docs)

# parallel chain: pass the question through + retrieve+format context
parallel = RunnableParallel({
    "context": retriever | RunnableLambda(format_docs),
    "question": RunnablePassthrough(),
})
chain = parallel | prompt | model | StrOutputParser()
```
Running "Who is the author of this book?" traces beautifully — the `RunnableParallel` (with the `RunnablePassthrough` branch yielding the question and the retriever branch yielding context), then `ChatPromptTemplate` (input: context + question), then `ChatOpenAI`, then `StrOutputParser` — each with latency and token usage.

**Two problems surface:**
- **Only the chain is traced.** The PDF **load/chunk/embed** part is *not* traced, because by default LangSmith only traces **LangChain runnables** (anything invoked via `.invoke`). Plain Python steps aren't traced.
- **Latency bug:** every run re-loads, re-chunks, and re-embeds the PDF (~200s each time). It should build embeddings once and reuse them.

### 4) Tracing non-runnables with `@traceable` (rag_v2)
Refactor load/chunk/embed into plain functions and decorate them so LangSmith traces them:
```python
from langsmith import traceable

@traceable(name="load_pdf", tags=["pdf", "loader"], metadata={"loader": "PyPDFLoader"})
def load_pdf(path):
    ...

@traceable(name="split_documents")
def split_documents(documents, chunk_size, chunk_overlap):
    ...

@traceable(name="build_vector_store", tags=["embedding", "vector_store"],
           metadata={"embedding_model": "text-embedding-3-small"})
def build_vector_store(documents):
    ...

@traceable(name="setup_pipeline")
def setup_pipeline():
    docs = load_pdf(pdf_path)
    chunks = split_documents(docs, 1000, 150)
    retriever = build_vector_store(chunks)
    return retriever

# query chain still gets a run name:
chain.invoke(question, config={"run_name": "pdf_rag_query"})
```
`@traceable` traces **any normal Python function** (even without runnables) and can attach per-component **tags and metadata** (searchable in the UI). After this, `setup_pipeline` shows `load_pdf` (input: path, output: 441 Documents), `split_documents` (input: chunk size/overlap), and `build_vector_store` (input: 441 docs, output: retriever) as three runs — with latency (PDF load ~15s, vector store build the slowest). Remaining nit: it creates **two separate traces** (`setup_pipeline` and `pdf_rag_query`) instead of one nested hierarchy.

### 5) Solving latency with FAISS index persistence (rag_v4)
Use **FAISS** as the vector DB. On first run, build the index and save it to the project directory; on subsequent runs, load the existing index instead of rebuilding.
- First run: build index (~30s). Subsequent runs: **load index → ~1.65s** instead of ~202s.
- **Index rebuilds when:** no index exists yet; the PDF content/metadata/size/last-modified time changes; chunking params (`chunk_size` / `chunk_overlap`) change; or the embedding model changes. Otherwise the existing index is reused (fast).
- This mirrors real production RAG — maintain a persistent index and query it repeatedly rather than re-embedding each time.

### 6) Tracing a ReAct agent
A ReAct agent with **two tools**: a **DuckDuckGo search** tool and a **weather API** tool. LangSmith exposes the full **Thought → Action → Observation** loop and the **agent scratchpad**:
1. Scratchpad initiated (empty).
2. ReAct prompt built ("Answer the following questions as best you can. You have access to the following tools…" + Thought/Action/Observation format + the question).
3. LLM decides the action (e.g., "search DuckDuckGo", action input "Dhadak 2 release date").
4. Tool runs; observation appended to scratchpad; prompt re-built with the observation; sent back to the LLM.
5. LLM emits the Final Answer.

You can watch **every intermediate state**, how one step's output feeds the next, and total tokens/cost/latency. A multi-tool query ("Identify the birthplace of Kalpana Chawla and then give its current temperature") forces both tools (search → "Karnal", then weather → "27°C"), and the longer trace shows each tool call recorded with full inputs/outputs.

### 7) LangGraph + LangSmith integration
LangSmith is **tightly coupled** with LangGraph (same team). Two rules to remember:
- **A whole graph execution = one Trace.**
- **Each node in the graph = one Run** inside that trace. (Also captures branching, conditional edges, parallel paths, and subgraphs.)

Example: an **essay evaluator** graph with 4 nodes — three parallel evaluators (language, analysis, thought/clarity), each producing a feedback + score, feeding a final node that produces an overall feedback and the average score.
- Each node's function receives the **state** as input; LangSmith shows that state in/out per node.
- **Structured-output LLMs** (`model.with_structured_output(EvaluationSchema)`) show a `RunnableSequence` + `RunnableLambda` (the lambda re-arranges the LLM response to the output schema), whereas the plain final-feedback LLM (no structured output) shows a simpler run.
- Optionally, node functions can *also* be decorated with `@traceable` to trace at the function level (the node is traced automatically regardless). You can inspect per-node latency (e.g., `evaluate_analysis` ~3.5s) and per-node cost.

## 🪜 Beyond Observability — LLMOps features (overview)
LangSmith does much more than observability; these all fall under the **LLMOps** umbrella.

### Monitoring & Alerting
> *Monitoring looks across many traces at once to track the overall health of your LLM system. It aggregates key metrics like latency, token usage, cost, error rates, and success rates. You can set up alerts to notify you when these metrics drift outside acceptable ranges.*

Observability studies a **single trace**; monitoring studies **many traces together**. The **Monitoring** tab (below Tracing Projects) shows graphs per project: traces per day, trace latency, error rate, total LLM calls, LLM-call latency, cost, cost per trace, input/output tokens (and per trace), tool usage, etc. You can create **custom alerts** on any metric (e.g., "alert if latency > 5s") so you're proactively notified before users are impacted at scale — "issues often appear first as patterns across multiple runs rather than a single trace."

### Evaluation
> *Evaluation in LangSmith helps you systematically measure the quality of your LLM outputs. You can run tests against gold-standard datasets or apply custom evaluation metrics such as faithfulness, relevance, and completeness.*

Because LLMs are probabilistic, a small change (prompt, model, retriever) can improve some cases and break others. Evaluation gives an **objective, repeatable** way to confirm a new version is actually better and to prevent regressions. LangSmith supports **automated scoring with LLM-as-a-judge**, **semantic similarity checks**, and **custom Python evaluators**, run **online or offline**. In the UI: a project's **Evaluators** tab lets you attach prebuilt evaluators (hallucination, conciseness, code checker, …) or define your own.

### Prompt Experimentation
> *Prompt experimentation lets you systematically test and compare different prompt versions. You can run A/B tests across prompts on the same dataset, track performance against evaluation metrics, and record outcomes over time.*

Answers "which prompt is better?" systematically rather than by eyeballing. The **Prompt Engineering → Playground** lets you set up a prompt, provide a schema/evaluation criteria, hit **Compare**, and test the same prompt across **different models**. LangSmith also supports **prompt versioning** and hosting/collaboration via **LangChain Hub** (including public prompts).

### Dataset Creation & Annotation
> *LangSmith provides tools to build datasets for evaluation and fine-tuning. You can do manual annotation and store dataset versions for reuse across projects.*

Evaluation needs a standardized dataset — either a public one or one you build for your use case. From a trace you can **Add to Dataset** (each becomes a row), then **annotate/label** responses (was the answer right or wrong) via the annotation queue. Datasets are versioned and reusable across any project in your account (e.g., accumulate common questions + expected answers to test future app versions).

### User Feedback Integration
> *It lets you capture thumbs-up/down ratings or structured feedback from users in production. Feedback is logged alongside traces, tied to the exact prompt, model, and state, and supports bulk analysis.*

Like ChatGPT's 👍/👎 buttons. Each trace has a **Feedback** section where the score is logged; aggregate sentiment is visible under Monitoring, so you learn what users like/dislike about the app.

### Collaboration
LangSmith is built for teams. Instead of emailing screenshots, you can **copy a shareable link** to any trace — a teammate opens it and sees the exact trace as-is. Combined with prompt versioning, invited collaborators, and shareable **custom dashboards**, it makes team debugging far easier.

## ⚠️ Gotchas & Tips
- **No code change needed to start tracing** — just set the `.env` variables (`LANGCHAIN_TRACING_V2=true`, endpoint, API key, project).
- **Setting `LANGCHAIN_PROJECT` in code overrides the `.env` project** — use a separate project per app for clean organization.
- **By default only LangChain runnables (`.invoke`) are traced.** Plain Python steps (PDF load/chunk/embed) are invisible until you decorate them with `@traceable`.
- **`@traceable` traces any function** and can attach per-component tags/metadata, which make traces **searchable** — invaluable when you have many traces.
- **Never re-embed on every request.** Persist a vector index (FAISS) and reuse it; know the conditions that force a rebuild (content/metadata/size/mtime change, chunking params, embedding model).
- **Observability = one trace; Monitoring = many traces; Alerting = threshold breaches.** Keep the distinction clear.
- **For complex LangGraph workflows and agents, always integrate LangSmith** — it's not only for debugging; it's also a great **learning tool** for understanding how a graph actually executes.
- **Delete your API keys after recording/sharing** if they were ever exposed (the instructor notes he removes his after shooting).

## 📌 Key Takeaways
- **Observability** answers *why* something happens inside a non-deterministic LLM system that leaves no error trace; **LangSmith** is the tool that provides it.
- Learn the hierarchy: **Project → Trace (one execution) → Run (one component)**.
- Tracing is enabled entirely via environment variables — zero app code changes to begin.
- LangSmith records inputs/outputs, every intermediate step, latency, tokens, cost, errors, tags, metadata, and feedback — at both app and component level.
- Use **`@traceable`** to trace non-runnable Python functions and to attach searchable tags/metadata.
- RAG best practice: **persist the vector index** and reuse it (huge latency win — ~202s → ~1.65s).
- Agents: LangSmith exposes the full **Thought → Action → Observation** loop and scratchpad, making autonomous behavior transparent.
- LangGraph: **graph execution = one trace, each node = one run**; captures branching, parallel, conditional, and subgraphs.
- Beyond observability, LangSmith supports **Monitoring & Alerting, Evaluation, Prompt Experimentation, Dataset Creation & Annotation, User Feedback, and Collaboration** — collectively the domain of **LLMOps**.
